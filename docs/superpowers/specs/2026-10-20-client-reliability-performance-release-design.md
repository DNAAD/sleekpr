# 客户端保存、预览性能与正式交付设计

## 状态与目标

状态：用户已确认规格及真实打印驱动线程暂不迁移的边界。业务实现待实施计划审阅并选择执行方式后开始；尚未提交或推送。

按以下顺序逐阶段实施与验证：

1. 保存冲突保护。
2. 隐藏窗口及 UI 线程减负。
3. 预览资源预算。
4. 版本识别与正式绿色包。

目标是防止编辑覆盖其他入口的数据、减少编辑卡顿、在分配大图片之前拒绝超预算请求，并明确操作者运行的是哪个版本。不改变正常标签的毫米坐标、打印 DPI、字段优先级和 Qt 原生输出。

## 方案选择与边界

| 方案 | 收益与代价 | 结论 |
| --- | --- | --- |
| 在各窗口分别增加保存和刷新判断 | 变更小，但并发规则及资源限制容易出现多个版本 | 不作为长期入口 |
| 集中保存协调、受控预览调度、统一资源预算，分阶段接入旧入口 | 可以分别回归，保留既有 UI 和 HTTP 行为 | 推荐采用 |
| 同时重写窗口、模板格式和打印接口 | 影响范围较大，难以隔离本轮收益 | 不采用 |

本轮不恢复标签复杂表格入口，不实施动态多页单据规格，不引入数据库、浏览器排版或新运行时依赖。保留未提交的 Harness 和其他设计文件。

真实打印引擎当前是同步接口，且被桌面与 HTTP 共用。本轮第二阶段只后台化可隔离的预览计算，不直接跨线程调用现有借用的 `LabelPrintEngine`。驱动后台提交、统一打印任务队列和任务历史不包含在本规格中；因此不宣称本轮能消除真实驱动阻塞。迁移驱动线程需单独设计其所有权、HTTP 响应及设备验收。

## 一、保存冲突保护

### 1.1 单一写入协调

新增基础设施层保存协调入口，负责状态读取、写入互斥、备份及原子替换。核心层只承载变更描述、比较规则和结构化结果，不新增文件系统业务。复用 `PrintClientSettingsJson`，不维护第二套序列化。

现有 `FileSettingsStore` 的兼容入口继续可用；生产写入路径必须纳入同一锁与备份机制，不能出现协调入口已经加锁而旧入口仍绕过锁写文件的情况。实施计划需逐一核对设计器、设置窗口、HTTP settings 及其测试调用者。

读取结果区分：文件不存在、正常读取、权限或 I/O 错误、JSON 损坏。启动时可以保持既有默认值兼容，但 UI 必须显示错误状态；损坏或不可读不能被自动保存当成合法空配置覆盖。

### 1.2 变更范围与冲突判断

客户端编辑以最后成功读取或保存的快照为基线，提交明确的修改范围，而不是无条件覆盖整份设置：

- 设计器只更新发生变化的模板槽位，包括模板字段名称与设备 profile，不写回其打开时缓存的默认打印机、Origin 或 HTTP 上限。
- 设置窗口按实际修改的设置字段及模板映射项提交；未修改的模板和外部变更保留。
- 同一字段或同一模板槽位在外部已发生变化，且与本次期望基线不同，返回保存冲突，不按时间顺序强行覆盖。
- 外部已保存与本次完全相同的目标值可视为幂等成功，不制造重复写入或冲突。
- 比较使用规范化的结构化值，模板使用完整模板序列化结果，不比较 UI 展示文字或不可靠的修改时间。

读取最新配置、检查基线、合并变更、备份和写入在同一文件锁保护下完成。跨进程锁使用 Qt 能力，锁等待有明确上限；锁失败不能无限阻塞 UI。

### 1.3 保存结果与草稿

保存协调返回成功、冲突、读取失败、备份失败、写入失败等结构化状态。修改设计器保存协调契约，使其能够知道写入是否成功，不能仅依靠 `void` 回调后继续显示成功。

失败时保留当前文档、输入框和撤销历史，成功基线不前移。冲突后停止重复自动保存同一冲突版本，界面提供重新读取外部版本或导出当前草稿的入口；重新读取需明确确认丢弃本地未保存修改，不默认强制覆盖外部版本。

### 1.4 备份与 HTTP 兼容

维护最近一次有效设置备份，损坏配置另保留原始字节用于恢复。写入必须先确认所需备份成功，再通过 `QSaveFile` 替换；恢复操作需要显式选择，不能静默加载旧备份后自动覆盖当前文件。

`GET/POST /settings` 的旧请求字段与响应包络保持兼容。旧 POST 是显式整体替换请求，不能悄悄解释为局部更新；其写入也使用统一锁、备份和读取错误处理。本轮不新增必填 revision，不宣称未携带版本信息的旧 HTTP 请求拥有乐观并发保护。

因此保护边界是：客户端差量保存会保留其他入口的无关改动，并在同一目标被改变时拒绝覆盖；旧 HTTP 整体替换仍保留既有显式替换语义。将来需要 HTTP 条件更新时，应作为独立兼容扩展设计。

### 1.5 验收

- 两个客户端快照修改不同目标，均可成功且互不覆盖；修改相同目标，旧快照被拒绝且草稿保留。
- HTTP 修改打印机或安全上限后，设计器保存模板不恢复旧设置。
- 新建文件、无变化保存、幂等保存、锁超时、权限错误、损坏 JSON、备份或提交失败均有回归。
- 保存失败不得触发成功提示或更新成功基线，不能丢失撤销与输入状态。

## 二、隐藏窗口及 UI 线程减负

### 2.1 通知与可见性

保存成功只发布与修改范围相符的通知。不再无条件执行完整的 `SettingsWindow::reloadFromDisk()` 和其他窗口刷新。

- 隐藏窗口只记录待刷新状态，不枚举打印机、重建表单或渲染图片；再次显示时按需读取。
- 可见设置窗口有未保存草稿时，不以外部刷新覆盖表单，转为冲突或外部更新提示。
- 工作台名称更新只更新名称和问题文案，不替换字段值或非法 JSON 草稿。
- 打印机、纸张或模板正文真正变化时，失效相应计划；纯名称变化仍不要求再次确认打印内容。

### 2.2 预览计算队列

为设计器和工作台引入职责聚焦的预览调度器，采用单个进行中任务加一个最新待处理任务。连续输入替换尚未开始的旧请求，不为每次按键堆积线程任务。

GUI 线程只读取控件、建立不可变快照和发布结果。后台仅执行可隔离的模板规划、文本测量及 `QImage` 绘制，不访问 QWidget，也不创建或更新 QPixmap。结果回到 GUI 后再更新图片。

每个请求含文档、真实或模拟输入、纸张、设备配置、缩放和屏幕像素比的快照及递增代号。只接受当前代号的结果；切换模板、修改输入、隐藏或关闭窗口都会使旧结果失效。关闭后不访问窗口成员，后台任务及共享缓存必须有明确生命周期。

不能安全中断的旧计算允许完成，但不得发布；新待处理请求和总并发均保持有界。不得用 `processEvents()` 在同步计算中模拟后台执行。

规划中的工作台立即禁用旧打印计划，不能在等待后台结果时打印旧数据。点击打印时仍执行当前数据与模板一致性检查，不放松原有二次确认语义。

### 2.3 份数校验与测量

将份数校验和总页数计算从实际页列表展开中分离。按钮状态和问题检查只使用元数据，不为更新状态构造完整重复页列表；实际提交前只展开一次，并保留完整页序及上限校验。

记录规划、栅格化、保存、隐藏窗口刷新次数及 UI 结果发布时间。使用相同构建模式和数据比较优化前后的 P50/P95，不在无基线时承诺具体延迟。覆盖普通标签、密集元素、数组及连续参数输入，仍使用模拟引擎而非真实打印。

### 2.4 验收

- 隐藏窗口收到变更不渲染；显示后更新一次，且不覆盖用户草稿。
- 慢任务 A 之后输入 B，最终只能显示 B；输入过程中不存在可点击的旧打印计划。
- 高频输入不会产生无界待执行任务，窗口关闭后回调无越界。
- 纯名称、份数与实际版式变化分别触发正确层级的检查；输入光标、焦点和撤销历史不回退。

## 三、预览资源预算

### 3.1 预算入口

预算结构集中定义，供桌面预览、HTTP PNG 和原生图片生成共同使用；不能只在某个窗口或路由补判断。

本轮新增预览默认预算：单边不超过 16,384 像素，单页不超过 64,000,000 像素；按实际像素格式计算预计图片字节。页数、批次数、JSON 响应字节继续使用已有可配置上限。新增像素预算先用有名常量集中维护，不另加一组设置控件。

上述预算只限制预览图像资源，不更改打印 DPI，也不静默降低用户指定的正式预览分辨率。超限需提示纸张、DPI、缩放或批次需要调整。

### 3.2 分配前检查与错误传播

在浮点值转换为图像尺寸、构造 `QImage`、编码 PNG 之前检查：纸张和 DPI 有限、尺寸为正、单边上限、乘法溢出、总像素及预计字节。桌面设计预览还包含缩放和设备像素比，不能只校验基础 DPI。

分阶段准备计划时尽早应用剩余页数及可计算的工作量预算，避免生成明显超限的完整结果后才拒绝。遇到无法提前精确预估的量，保留渲染过程中累计预算检查，不宣称入口字节上限等于内存上限。

图像分配失败、绘制失败或 PNG 保存失败必须向上传播结构化原因，不能返回空 Base64 并宣称成功。资源超限沿用 HTTP 413 / `REQUEST_TOO_LARGE`；其他渲染失败沿用现有失败包络，不根据错误文案判断状态码。

响应大小采用累计页编码尺寸与包络开销检查，最终序列化再精确校验，避免每加入一页就重新序列化整个 Base64 页面集合。检查必须计入 JSON 转义、逗号及页数变化，不能使用漏算的估计作为最终门槛。

### 3.3 验收

- 构造超宽、超高、极端 DPI、缩放与非法非有限值，在分配图片前拒绝。
- PNG 即使压缩后很小，也不能绕过像素预算；边界内输出不改变毫米布局和 DPI。
- 单条、批量、桌面预览及失败编码路径都不返回伪成功。
- 响应预算的边界、页数变化和多页累计有回归，保持旧正常请求的响应结构。

## 四、版本识别与正式绿色包

### 4.1 可追踪版本

集中生成构建信息，包括项目版本、Git 提交号、工作区是否有源码改动、Debug/Release 模式。构建信息变更需能触发正确增量更新，不能长期保留首次配置时的旧提交号。

应用设置 Qt 版本信息，并提供可查看和复制的版本诊断入口：程序路径、构建信息及配置路径。启动日志记录相同信息，不把机器专属绝对路径编进二进制常量，不展示或导出设置中的敏感内容。

启动器在启动前明确目标模式、文件路径及构建标识；保留 `-Mode`、`-Rebuild`、`-NoLaunch` 现有语义，不每次无条件重建，也不把 Debug 构建宣称为 Release 更新。

### 4.2 绿色包

复用现有独立 Release 构建及 `windeployqt` 流程，输出绿色目录和 zip，不新增安装器、签名或在线更新系统。修正打包脚本中版本和压缩包名称的重复硬编码，使用统一项目版本来源。

包内提供构建清单，包含版本、提交、源码修改状态、构建模式及必要文件摘要。归档使用已部署的 Release 目录，不包含 PDB、测试配置、操作员数据或临时日志。源码未提交时如实标记，不为了得到干净标识擅自提交现有改动。

打包前运行 Release 测试，打包后从输出目录执行隔离的版本读取与设计器启动冒烟。失败时不得报告正式包完成。验证不启动正常托盘服务，不读写用户配置，也不发送真实打印；物理出纸验收另由用户明确授权。

涉及清理构建或发布目录前，解析并验证绝对路径位于当前仓库预期目录，不能对未验证的计算路径递归删除。占用程序需用户先保存并退出，不默认使用 `-StopRunning` 强杀。

### 4.3 验收

- Debug 与 Release 清晰可辨，应用、启动日志和包内清单指向同一构建标识。
- 仅改变 Git 状态或构建配置后，增量构建不会继续报告旧标识。
- 绿色目录在隔离检查中能加载 Qt 插件并启动设计器；压缩包及清单与产物一致。
- 脚本任一步失败立即终止；测试跳过必须明确标注为未完成验收，而不是通过。

## 分阶段交付约定

每阶段先观察新增回归失败，再实施，完成单项和全量验证后进入下一阶段；GUI 测试串行执行。阶段之间保留对旧 JSON、HTTP 包络和原生绘制计划的兼容覆盖。

规格批准后再编写实施计划，列出实际文件、测试入口、线程及持久化迁移顺序。用户未明确要求时，不提交、推送、强杀进程或执行真实设备打印。现有 Harness 和动态单据规格不随本轮自动合并或改写。
