# 后台保存队列与统一退出保护设计

## 一、状态与目标

状态：已按用户选择完成当前对话顺序实施及独立整体复核，复核发现已补回归修复。最终 Debug/Release CTest 各 34/34，通过原生隔离冒烟；未提交、未合并、未推送或重新打包。

目标是把设计器和设置窗口的 `settings.json` 保存移出 GUI 线程，同时保证连续编辑不丢失、外部冲突不被掩盖、真正退出前不会静默放弃草稿或中断写入。

成功标准：

- 磁盘读取、差量计算、序列化、备份和提交不在编辑回调中同步执行；慢磁盘不阻塞正常输入。
- 连续输入只合并尚未开始的保存意图，已开始的写入必须有明确结果。
- 旧保存成功不会覆盖新输入、撤销结果、非法 JSON 原文或更新的“应用但不保存”状态。
- 保存失败、冲突或非法草稿默认阻止真实退出，由用户明确选择处理方式。
- 关闭普通窗口仍然隐藏到托盘，不能把窗口关闭等同于退出程序。

这是应用级保存调度和生命周期改造，不是打印驱动后台化，也不承诺解决所有界面卡顿。

## 二、范围与方案

### 2.1 纳入本轮

- 标签设计器对 `settings.json` 的自动保存。
- 设置窗口对同一文件的显式保存、重新读取和备份恢复。
- 共享保存服务、会话状态和保存反馈。
- 托盘及其他应用自有退出入口的统一保护。
- 退出期间可恢复的操作准入控制，以及异步服务的安全收束。

### 2.2 不纳入本轮

- 模板库、纸张规格库、字段预设库的存储迁移或后台保存。
- 工作台业务输入持久化、跨进程草稿恢复和新的自动恢复文件格式。
- HTTP 请求整体异步化、HTTP 保存队列改造、必填 revision 或接口字段重构。
- 真实打印驱动线程迁移、打印任务历史或强制取消已提交打印任务。
- 新增复杂表格功能、设计器整体重写和 Release 打包流程修改。

上述独立存储窗口可在退出等待期间暂时禁止新操作，但本轮不声称保护它们尚未提交的每一项表单输入。系统强制终止、断电、崩溃和操作系统强制关机不属于正常退出保证。

### 2.3 方案比较

| 方案 | 特点 | 结论 |
| --- | --- | --- |
| 每个窗口各自增加线程和退出判断 | 修改局部，但同文件协调、任务寿命和错误处理重复 | 不采用 |
| 应用持有共享保存服务与退出协调器 | 统一串行写入、保留会话隔离，复用既有仓库 | 采用 |
| 同时迁移所有存储和 HTTP、打印任务 | 范围大，难以单独验证保存和退出安全 | 留待后续 |

## 三、实施前现状与目标分层

实施前的 `SettingsEditSession` 同步调用 [SettingsRepository](../../../src/infrastructure/settings/SettingsRepository.cpp)。设计器保存成功后会用返回快照替换 `m_settings`；设置窗口保存成功后会重新读盘。直接把这些调用搬到线程，会引入旧结果回写和保存基线失配。

实施前 [main.cpp](../../../src/app/main.cpp) 的托盘退出直接连接 `QApplication::quit`，没有保存完成前的统一协调。预览已有独立执行器，但其“旧结果可丢弃”规则不能用于持久化任务。

| 层次 | 本轮职责 | 边界 |
| --- | --- | --- |
| `core` | 保存意图、修订标识、状态转移和可测试的基线协调规则 | 不访问文件、控件或托盘 |
| `infrastructure` | 专用保存执行器；复用仓库的锁、原子写入和备份 | 不读取窗口成员，不复制序列化规则 |
| `app` | 保存会话协调、窗口语义接入、状态展示、退出协调和应用组装 | 不在窗口中实现文件合并算法 |
| `http` | 保留正常接口契约，仅在退出等待期阻止新操作进入 | 不随本轮迁移为异步路由 |

拟使用职责名称 `SettingsPersistenceService` 和 `ApplicationExitCoordinator`；具体拆文件及接口签名在实施计划中确定。优先改造现有会话边界，不保留两套相互竞争的同步、异步生产保存状态机。

## 四、后台保存队列

### 4.1 所有权与线程

保存服务由应用持有，寿命覆盖窗口及已接受的任务。使用专用单工作线程执行保存，不占用预览工作池，不为每次编辑创建线程。

GUI 线程负责读取控件、更新有效模型、冻结输入和发布结果。工作线程接收值对象，完成差量构造、规范化、读盘、校验、备份和原子提交；不能持有 QWidget、QPixmap、借用的窗口成员或跨线程读取 GUI `QPointer`。

工作结果经服务回到 GUI 线程；窗口观察者不存在时只停止界面通知，不把已接受的保存悄悄取消。应用销毁前必须先收束保存执行器，不能等事件循环结束后才启动异步保存。

### 4.2 有界调度

- 同一设置文件的写入串行执行；本轮只有设计器和设置窗口两个主要编辑会话。
- 每个会话至多保留一份最新的待处理累计保存意图；服务至多执行一个磁盘操作。
- 合并只替换同一会话尚未开始的意图，不能丢弃其他会话的请求。
- 完成当前操作后公平调度各会话，连续自动保存不能使显式保存长期得不到执行。
- 正在执行的提交不强制取消、不终止线程；用户后续编辑进入新的待处理意图。
- 不以无限重试或无限队列处理磁盘错误。失败暂停该会话，保留最新草稿供显式重试或重新读取。

这里的“累计意图”是该次请求范围内希望最终保存的内容，不是最后一个控件事件。设置窗口只有点击保存或退出时明确选择保存，才接受其对应快照；之后仅编辑或“应用但不保存”的内容不得混入已经接受的请求。

## 五、编辑、保存和冲突语义

### 5.1 分开跟踪四类状态

1. 用户观察到的编辑基线，包括原始 JSON 中的未知扩展。
2. 当前有效草稿及独立的非法编辑器原文。
3. 本会话已成功提交的内容，以及已接受但尚未完成的保存目标。
4. 仅应用到运行中、尚未请求保存的设置。

请求至少带会话标识、会话代次、编辑修订和操作标识。只有 `Saved/Unchanged` 可确认成功；失败不能推进成功基线。撤销历史在语义编辑时建立，后台完成通知不能再次制造撤销点。

### 5.2 旧结果不能回写新草稿

保存修订 A 执行时用户已编辑到 B，A 完成只确认 A 已落盘；不能执行整份 `m_settings = result.snapshot.settings`、全表单重读或把 B 标成已保存。

后续请求根据本会话确认结果协调基线。尤其需要覆盖“编辑到 A 后，在 A 写入途中撤销回最初内容”的情况：即使当前内容等于最初基线，也要保留恢复意图，避免 A 完成后磁盘留下已被用户撤销的修改。

未触及的界面输入、焦点、光标、选择和非法模拟 JSON 原文保持不变。外部变更仍按现有可见性、草稿保护规则处理，不能借保存完成强制刷新全部窗口。

### 5.3 只认可自身写入，不吞掉外部冲突

协调自身前序写入时，只调整本会话确实成功提交目标的期望值，不能把结果快照中所有字段都当成用户已经看过的新基线。

例如：会话保存了打印机，同时结果中读到了外部新改的 HTTP 上限；用户随后基于旧值编辑该上限，仍应检查原来的观察基线，不能因为前一次保存“看见了”外部值而无条件覆盖它。

设计器继续按模板槽位检测冲突，设置窗口继续按实际变化字段合并；保留字面路径、可选值语义和未知扩展。自身写入的协调不能放宽另一个会话或 HTTP 写入造成的冲突。

复用 [SettingsChangeSet](../../../src/core/settings/SettingsChangeSet.cpp) 与仓库原始 JSON 合并规则。不得仅用 typed 差异丢掉 `sourceExpected`，也不得盲用整个最新快照重建所有原始期望值。

### 5.4 “应用但不保存”保持独立

设置窗口的该操作仍然只改变运行时设置，不自动提交到保存服务。

若保存 A 尚未完成，用户又应用 B，则 A 的完成通知不能把当前运行状态退回 A，也不能把 B 一并写盘。持久化通知与运行时应用使用独立顺序标识；后发生的显式运行时应用优先。

表单未修改的兜底显示值仍不算用户修改，特别是可选 HTTP 上限。成功后的通知仅告知相关范围，不无条件枚举设备或触发完整预览。

### 5.5 失败、重读与恢复

| 结果 | 后续行为 |
| --- | --- |
| `Saved/Unchanged` | 确认对应目标；没有更新草稿或其他阻断项时才显示已保存 |
| `Busy/BackupFailed/WriteFailed` | 保留目标和草稿，暂停自动重试，提供显式重试 |
| `ReadFailed` | 保留草稿及读取错误，禁止以默认值覆盖；提供重读或既有恢复入口 |
| `Conflict` | 暂停该会话；不能靠反复重试旧基线强制覆盖，需显式成功重读或恢复 |

重读、恢复也是与写入串行的控制操作。用户确认后取消该会话尚未开始的旧保存意图，等待已开始写入结束，再执行控制操作；不能边写边重置基线。

只有控制操作成功才替换该会话模型并开始新代次。失败保留草稿、最近已确认的成功基线及本次错误，不自动重放被取消的旧请求，也不撤销控制操作之前已确认的自身写入。其他会话不被隐式重置；整文件恢复后，其旧草稿仍必须经过冲突判断。

继续使用 `.bak`、`.corrupt.bak`、`.restore.bak` 的既定含义。恢复摘要来自最近一次实际观察或失败快照，不能盲用过时的成功摘要。存储保证详见 [设置保存与恢复](../../../.harness/wiki/settings-persistence.md)。

## 六、保存反馈与窗口关闭

界面以紧凑状态显示 `待保存`、`正在保存`、`已保存`、`保存失败` 或 `存在冲突`。未提交保存的设置表单显示 `未保存`；非法原文显示原有行列提示并计入未保存状态。

保存 A 成功但 B 仍排队时，不短暂显示“全部已保存”。其他合法属性保存成功也不能清除非法 JSON 的脏状态。

普通关闭行为：先提交有效的待应用编辑和自动保存计时器，然后隐藏窗口。仅有正常排队写入时无需等待磁盘；失败、冲突或非法原文仍保留现有确认及本次运行内重开继续编辑的能力。

设置窗口没有点击保存的表单不因隐藏自动保存；再次打开保留草稿。设计器尚有草稿或排队任务时复用原会话，不能由 `openDesigner` 销毁并用旧磁盘重建。

## 七、统一退出保护

### 7.1 入口与状态机

所有应用自有真实退出入口调用退出协调器，不再直接调用 `QApplication::quit`。普通窗口关闭不进入该流程；启动错误和独立冒烟测试的无草稿提前返回不伪装成交互式正常退出。

状态流为 `运行中 -> 收集草稿 -> 等待保存 -> 可退出 -> 正在退出`；发现问题进入 `退出受阻`，取消则回到 `运行中`。退出请求带独立代次，反复点击只激活现有退出提示，不能重复提交或产生多个退出流程。

### 7.2 收集与等待

1. 暂停新用户修改和重型操作；保留各控件原有启用状态。
2. 结束当前有效编辑动作，冲刷设计器待应用计时器，确定本次退出需要完成的保存目标。
3. 汇总两个窗口的非法原文、失败、冲突、正在执行与排队目标，以及设置窗口未请求保存的表单。
4. 对未请求保存的设置显示明确选择：`保存并退出`、`不保存并退出`、`返回编辑`，默认返回编辑。不以“应用过”代替保存授权。
5. 在 GUI 事件循环继续运行时等待已确认目标和在途操作结束，展示状态；不能在 GUI 上阻塞等待工作线程。
6. 无阻断草稿、待处理保存和在途写入后，才允许真正退出并收束执行器。

若已有 GUI 定时器接受了真实打印提交，应等待其既有调用收束后再退出，不强行销毁借用引擎，不承诺撤销系统打印队列；本轮不扩展新的打印任务系统。

### 7.3 阻断与用户选择

非法 JSON、保存失败或冲突默认阻止退出，集中列出来源和原因，提供：

- `返回编辑`：恢复正常运行及原窗口草稿，取消本次退出目标。
- `重试保存`：仅重试仍然有效且允许重试的保存目标；冲突和非法输入需回原界面处理，不绕过验证。
- `放弃未保存内容并退出`：明确二次确认，取消尚未开始的保存和草稿后退出。

放弃不等于回滚：已经完成的自动保存不会撤销，正在执行的原子写入仍需完成并报告结果。只有处理完在途写入后才能退出，不能以“强制退出”按钮终止线程。

等待期间可返回编辑；取消退出不会取消已开始保存，过期退出回调不得稍后自动退出。不能恢复时无差别启用所有控件，导致原本因校验而禁用的功能被开启。不设置超时后静默退出策略。

### 7.4 退出期准入控制

保存收束阶段暂停新写入和重型预览/打印入口，取消退出后恢复。HTTP 监听不关闭重绑，避免取消后端口被其他进程占用。

退出等待期继续允许 `GET /health`；其余到达路由的新请求按现有 JSON 错误包络返回 `503 Service Unavailable`，错误码 `CLIENT_EXITING`。既有请求大小、安全和解析检查仍适用；正在分段接收的请求只有通过路由准入检查才可执行业务。

已经进入执行的同步请求先完成，桌面写入仍由仓库锁协调。此门禁只覆盖正常退出的短暂阶段；运行中 `/settings`、预览和打印契约保持不变，HTTP `POST /settings` 仍是显式整体替换。

最终退出先禁止继续接受任务并结束存储写入，再按寿命关系收束预览和窗口。`aboutToQuit` 可作诊断与最后清理，不能成为第一次收集草稿和启动异步保存的位置。

## 八、测试与验收

实施时先添加失败测试，再修改生产代码；本规格阶段不运行构建、打印或交付操作。

| 类别 | 必须覆盖 |
| --- | --- |
| 队列与响应性 | 用可控写入屏障证明 GUI 事件可继续处理；高频编辑队列有界；显式保存不饿死 |
| 连续编辑 | A 执行时编辑 B、撤销回原值、未开始请求替换、旧成功不覆盖新草稿 |
| 并发基线 | 同会话前序写入不自冲突；不同会话同目标冲突、不同目标合并；未知扩展及未观察外部字段保护 |
| 设置授权 | 保存 A 后只编辑或应用 B，B 不随 A 写盘，运行时 B 不被 A 完成回退；兜底值不变成隐式修改 |
| 文件失败 | 锁忙、损坏、读失败、备份失败、原子提交失败均保留草稿且不产生成功通知，不无限自动重试 |
| 控制操作 | 重读/恢复与写入有序，失败不重置草稿；旧代次不回写；恢复摘要和备份来源保持有效 |
| 窗口寿命 | 隐藏后继续保存、重开复用草稿、观察者销毁不丢已接受任务、回调不访问已销毁成员 |
| 正常退出 | 活跃写入、排队目标、待应用计时器、未保存设置、非法原文、错误及冲突分别阻断或完成 |
| 退出撤销 | 重复请求幂等、等待时返回、恢复原启用状态、旧退出回调不能终止已恢复的运行 |
| 放弃退出 | 丢弃未开始目标，但等待执行中写入；明确不回滚已保存内容 |
| HTTP 门禁 | 等待期只放行健康检查，拒绝其他新操作；取消恢复准入，不改变正常路由契约 |
| 应用收束 | 独立临时配置运行退出冒烟，不开启生产端口、不发送真实打印、不依赖用户配置 |

异步测试使用可观察状态或显式屏障，不依赖固定 20/30ms 等待。性能比较使用相同 Release 构建、相同样本和连续输入/拖拽流程，分别记录 GUI 入队与后台落盘时间，不把不同构建模式的数据混作收益证明。

复用现有有界性能诊断，不记录标签实际内容或客户数据。最终按 [验证技能](../../../.harness/skills/verification/SKILL.md) 运行相关测试、完整 Debug/Release 回归和 JS 测试，报告实际结果，不把历史测试数量写死为本轮门槛。

## 九、风险与约束

- 主要风险是自身写入基线协调错误、旧完成覆盖新草稿和退出取消后的延迟退出；应作为独立领域/协调测试重点，不藏在窗口槽函数里。
- 文件锁只协调遵守同一锁协议的入口，不提供任意外部编辑器的事务保证；保留原有冲突保护边界。
- 背景任务不得依赖 GUI 事件循环之外才开始的收尾；不使用线程强杀、递归 `processEvents()` 或固定超时掩盖生命周期问题。
- 所有关键代码注释必须中文，维持原生 Qt 预览和打印链路，不新增第三方运行时，不使用 CodeRabbit。
